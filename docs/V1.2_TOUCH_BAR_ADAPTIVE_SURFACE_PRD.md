# LumiaKeys V1.2 补充 PRD：分层自适应快捷键表面

| 项目 | 内容 |
| --- | --- |
| 状态 | 已实现最小闭环（2026-07-24） |
| 基线 | LumiaKeys V1.2 Desktop-driven shortcut platform |
| 范围 | Android 手机端、Desktop Companion、共享协议 |
| 术语澄清 | 用户口述的“Codex 连接”指 LumiaKeys Desktop Companion 同步的 **Codex 应用工作区**，不是新的手机服务、账号连接或第二个控制通道。 |

## 1. 目标与问题

手机不能把下列三件事混成一个“已连接”状态：

1. **蓝牙 HID**：Android 手机是否作为键盘/鼠标连接到电脑；
2. **Desktop 同步**：LumiaKeys Desktop Companion 是否可达，并已通过已认证的局域网通道完成 manifest 同步；
3. **前台应用工作区**：Desktop 是否识别当前前台应用，且该应用已安装、正在运行、已配置可用布局和动作。

目标是把手机升级为类似 Touch Bar 的分层自适应控制表面：永远保留可用的通用快捷键；Desktop 可用时呈现其权威布局；当前前台应用可用时优先呈现专属快捷键。用户不应因为 Desktop、Codex 或某个应用未连接/未安装而看到近乎空白的主控制区。

## 2. 非目标

- 不新增手机到 Desktop 的任意命令、任意路径、Shell、Macro 或 Script 执行能力。
- 不改变 Android 本地 Profile、蓝牙 HID、滚轮或触控板的持久化所有权。
- 不实现 V1.3 WebSocket 配对、云同步、iOS、跨网发现、多页文件夹或通用未知应用的自动配置。
- 不把“进程在运行”误报为“前台应用已识别且动作可执行”。

## 3. 产品原则

- **Desktop 是唯一数据源。** Desktop 持久化应用、安装/运行/前台状态、布局、图标和动作映射；Android 只保留内存投影。
- **三层状态独立可见。** HID 已连不代表 Desktop 已同步；Desktop 已同步不代表已有可用前台应用。
- **始终可操作。** 无 Desktop 或同步失效时仍显示本地 General/Profile HID 控件。
- **优先但不伪造。** 前台应用只有同时满足“Desktop 已同步、已检测、运行、前台、存在非空布局”才可抢占默认表面。
- **ID 而非能力。** Android 仅发送 `buttonId`、`applicationId`、`profileId`；Desktop 再校验并执行。

## 4. 用户状态矩阵

| HID | Desktop 发现/同步 | 前台应用 | 默认主表面 | 右上角状态按钮 |
| --- | --- | --- | --- | --- |
| 未连 | 未发现 | 不可用 | 本地 General/Profile（可编辑；发送 HID 时由现有状态提示失败） | `HID`（离线色） |
| 已连 | 未发现 | 不可用 | 本地 General/Profile，绝不空白 | `HID`（连接色） |
| 任意 | 已发现、同步中 | 不可用 | 本地 General/Profile，等待同步，不使用旧缓存驱动操作 | `Desktop`（同步中色） |
| 任意 | 已同步 | 无法识别或不是已配置应用 | Desktop 的当前通用布局 | `Desktop` |
| 任意 | 已同步 | 已识别但没有布局/动作 | Desktop 通用布局 | `Desktop` |
| 任意 | 已同步 | 已检测、运行、前台且布局可用 | 前台应用专属布局 | `<应用名>` |
| 任意 | 曾同步、现已断开 | 旧 manifest 可能仍在内存 | 本地 General/Profile；旧 manifest 只可用于诊断 | `HID` |

`HID: Offline` 不禁用 Desktop-only managed actions；`Desktop: Offline` 不会禁用本地 HID 配置。三者的可用性由各自传输层决定。

## 5. 信息架构与具体 UI 行为

### 5.1 固定层

主界面不再占用整行显示三个状态。滚轮/触控板右上角的控制菜单按钮同时承担单一状态显示，并按 `前台应用 > Desktop > HID` 自动切换：识别到可用前台应用时显示应用名；Desktop 已连接但应用未知时显示 `Desktop`；没有 Desktop 时显示 `HID`。Tooltip 和控制菜单仍提供完整连接说明。

Desktop 离线时保留 General、Web、Zoom / Teams、Custom 等本地 Profile。Desktop 同步后，横向条只保留 General 作为显式 HID 降级入口，并隐藏 Web、Zoom / Teams、Custom。Apps 只在 Desktop 已同步且有已检测应用时出现。macOS 的 `ChatGPT` 被映射为 Desktop-owned `codex` 应用，手机显示统一的 `Codex / ChatGPT` 工作区。

### 5.2 表面选择优先级

默认选择规则（高到低）如下：

1. 当前前台应用的 Desktop-owned layout；
2. 已同步 manifest 的 `currentProfile` 通用 layout；
3. Android 本地当前 Profile（General 等）。

默认状态会跟随前台应用；用户在横向条点选一个运行中的应用、Apps/Codex 或本地 Profile 后，保留该手动选择，避免桌面焦点短暂变化打断操作。点击 Apps 中任何应用会发送 `applicationId` 并立即打开该应用的快捷键页，不等待进程监测下一轮；手机仍不接收桌面可执行信息。

### 5.3 状态文案、优先级和颜色

实际 UI 沿用现有英文界面：`HID: Connected/Offline`、`Desktop: Synced/Syncing/Offline`、`App: <name>/Unknown/No actions/Unavailable`。中文产品文案分别为“蓝牙 HID 已连接/未连接”“桌面已同步/同步中/离线”“前台应用：名称/未知/无可用动作/不可用”。

颜色优先级为：前台可用绿色；HID 已连蓝色；同步完成绿色；同步中中性；无动作黄色；离线和不可用灰色。任何错误提示属于现有连接页/错误区域，不能用错误红色覆盖一个实际仍可用的本地 HID 表面。

## 6. 应用安装、打开和识别的降级

- **未安装/未检测：** Desktop 不把应用发给 Android；Apps 和 Codex 不出现该项目。
- **已安装但未运行：** 出现在 Apps 启动网格；不成为前台工作区。
- **运行但非前台：** 可出现在 Workspace 横向条供用户选择；默认不抢占当前主表面。
- **前台但未知：** 显示 `App: Unknown`，保留已同步通用布局。
- **前台已识别、布局缺失或为空：** 显示 `App: No actions`，回退已同步通用布局。
- **Companion 断连：** 不以缓存 manifest 冒充“已同步”；立即回退本地 Profile。蓝牙 HID 若仍连接，继续正常发送本地键盘/鼠标报告。
- **只有 HID：** 不要求 Desktop，不显示空状态页；用户始终可执行本地通用快捷键。

## 7. 协议与数据模型约束

在兼容 schema v1 的增量字段中，`RemoteApplication` 新增可选布尔值 `foreground`，旧客户端/旧 manifest 省略时默认为 `false`。Desktop 刷新时根据平台前台窗口/进程名将状态映射到它拥有的应用 ID；同步只包含 `detected == true` 的应用，且 manifest 最多一个 `foreground == true`。

这个字段是**显示状态**，不是从手机接收的执行参数。Android 使用以下判断：

```text
foreground-ready = desktopSynced
                 && detected && running && foreground
                 && layout exists && layout.buttons is not empty
```

`desktopSynced` 必须同时满足：当前发现到 authenticated Companion host、同步状态为 `ready`、内存中有 manifest。保留最后一个 manifest 用于诊断/重连，但 host 过期后不得参与选择规则。

请求模型保持 `RemoteActionRequest.button(buttonId)`、`launchApplication(applicationId)`、`switchProfile(profileId)`。Desktop 必须对每一个 ID 在当前 manifest 中校验后才执行。Macro/Script 仍是协议保留枚举，在 Desktop `DesktopActions` 中明确拒绝；Android 不接受并且不执行路径、命令、脚本或原始快捷键 payload。

## 8. 验收标准

1. 右上角状态按钮按“前台应用、Desktop、HID”优先级显示一个状态；底层三种状态仍独立建模。
2. HID 已连而 Desktop 离线时，15 键本地通用网格可见且不被空页替换。
3. Desktop 已同步、无可用前台应用时，展示 Desktop 通用 layout；`App: Unknown` 或 `App: No actions` 与实际原因匹配。
4. 已同步的 VSCode 等应用被标为前台后，默认显示其 layout；点击按钮只提交其 `buttonId`。
5. Companion host 超时后，即使 `manifest` 仍存在，手机回退本地 Profile 并显示 `Desktop: Offline`。
6. 未检测的应用和 Codex 不显示为可启动工作区；已检测应用才进入 Apps。
7. protocol 校验拒绝多个前台应用；旧 JSON 缺少 `foreground` 仍可解析。
8. Desktop 与 Android 均不新增任意命令、路径、脚本或 Macro 执行通道。
9. macOS 菜单栏持续显示 template 模式的 LumiaKeys 图标；Desktop 设置窗口底部显示同步、手机和前台应用状态。
10. Apps 中打开任意已配置应用后立即进入其快捷键页；Chrome 默认布局覆盖书签、前后标签页、前进/后退、复制/粘贴、密码管理、播放/停止/静音等常用动作。
11. Chrome 的 3 × 5 页面已有 15 个动作，Page Up / Page Down 暂不挤占现有常用动作；鼠标触控板最右侧提供独立单指滚动区，竖直滑动只发送滚轮事件，不触发移动、左键或右键。

## 9. 发布与测试计划

自动化：共享协议 round-trip/同步过滤/单前台约束；Desktop discovery state 的同步；Android controller 的状态模型；390×844 widget 状态切换、前台优先和断连回退；现有 HID、manifest 和 action-ID 测试回归。执行 `flutter analyze`、根目录 `flutter test`、协议 `dart test && dart analyze`、Companion `flutter analyze && flutter test`，并构建 Android debug APK 与 macOS debug（在 macOS）。

触控板回归：验证普通区域仍支持单指移动/点击、双指滚动/右键；最右侧滚动区的单指上下拖动转换为滚轮步进，且不产生鼠标移动或点击。Chrome layout 保持 15 个动作，并显式验证未加入 Page Up / Page Down。

真机验收：用 Android 9+ HID Device 手机配对电脑；依次验证“仅 HID”“HID + Desktop 已同步”“切换到 VSCode/Codex 前台”“关闭应用”“杀掉/断网 Companion”；确认 Desktop 的 macOS 辅助功能权限或 Windows 前台窗口权限满足实际快捷键注入。模拟器不能证明蓝牙 HID 报告和真实 OS 前台窗口识别。

发布前不推送、不打 Tag、不发布资产；Windows/Linux 的前台识别和原生运行验收必须在各自系统完成。
