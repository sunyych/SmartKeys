# LumiaKeys V1.3 PRD — Dynamic App Workspace

| Field | Value |
| --- | --- |
| Status | Ready for implementation |
| Type | Incremental release based on V1.2 |
| Product area | Desktop, Android, iOS, shared protocol |
| Triage | `ready-for-agent` |
| Updated | 2026-07-17 |

This PRD specifies only V1.3 additions. V1.2 behavior remains supported and is
not restated here.

## Problem Statement

LumiaKeys currently requires the user to choose a shortcut context manually.
The phone does not continuously reflect which applications are running or
which application is in the foreground on the computer. That creates friction
when a user moves between Chrome, VS Code, Photoshop, Spotify, and other tools:
the computer context changes immediately, but the control surface does not.

The product also lacks a common real-time transport and pairing model for an
iOS client. Android can use Bluetooth HID for simple input, but app activation,
launching, URLs, Codex operations, and future complex actions require Desktop.
Without a shared session protocol, Android and iOS cannot consume the same
dynamic Workspace state or use one consistent Desktop execution pipeline.

## Solution

Add Dynamic App Workspace as an incremental Desktop-owned runtime model.
LumiaKeys Desktop monitors running and foreground applications on macOS and
Windows, resolves them to managed Workspaces, and publishes an ordered
Workspace list to connected phones. The phone renders that list in the existing
top Profile strip. General remains first; application Workspaces appear and
disappear from Desktop state; Codex remains a normal editable Workspace.

When automatic switching is enabled, a foreground-app change selects the
matching Workspace on connected phones. When a user selects an application
Workspace on a phone, Desktop optionally activates that application. Pinned
Workspaces remain visible while their applications are not running. Unknown
applications receive a safe Generic Layout and can be promoted into managed
profiles from Desktop.

Introduce a paired WebSocket protocol for real-time state and actions. Android
uses Hybrid Mode: simple keyboard/media input prefers Bluetooth HID, while
Desktop-only actions use WebSocket. iOS uses the same Flutter UI and Workspace
model but sends every action to Desktop and does not expose Bluetooth HID.

## Implementation Decisions

### Incremental compatibility boundary

- V1.3 adds protocol version 3 and manifest schema version 2. It does not
  reinterpret a V1.2 message with new semantics.
- Desktop continues serving the V1.2 authenticated HTTP manifest/action API for
  protocol-v2 Android clients. V1.3 clients prefer the paired WebSocket path.
- Android retains the complete offline Profile, key grid, wheel, touchpad, and
  Bluetooth HID path. Dynamic Workspaces enhance it only while Desktop state is
  available.
- The existing top Profile strip becomes the Workspace strip. No bottom or
  side navigation is introduced. Settings remains in the existing control
  menu rather than becoming a Workspace.

### Runtime application monitoring

- Introduce a deep `RunningAppMonitor` interface that emits immutable runtime
  snapshots containing running apps, the foreground app, and a monotonic
  sequence. Desktop orchestration does not depend on platform-native types.
- The macOS adapter uses `NSWorkspace` running-application state plus launch,
  terminate, and activate notifications. Its canonical app identity is the
  bundle identifier, with the normalized bundle URL as a fallback.
- The Windows adapter uses Win32 process enumeration for the running set and a
  foreground-window event hook for activation. Its canonical app identity is a
  normalized executable identity; helper and child processes are folded into
  their configured parent application when known.
- Native events drive ordinary updates. A low-frequency reconciliation pass
  repairs missed events; Desktop must not continuously poll at UI-frame rates.
- LumiaKeys Desktop, operating-system shells, launchers, transient dialogs,
  background-only agents, and configured ignored apps do not create automatic
  Workspaces.
- Foreground changes are coalesced for a short stability window before being
  published. The implementation may tune the window, but tests use an injected
  clock rather than wall-clock sleeps.

### Workspace domain model

- Introduce a deep `WorkspaceRegistry` that accepts persisted app/profile
  configuration and an `AppRuntimeSnapshot`, and produces one deterministic
  `WorkspaceState` for all transports and UIs.
- A Workspace descriptor contains a stable Workspace ID, canonical app ID when
  applicable, display name, icon reference, layout ID, profile ID, type,
  running/foreground/pinned/ignored flags, activation capability, and source.
- Workspace types are General, Application, Codex, and Generic. Generic is a
  safe runtime fallback, not a new executable action type.
- The visible list is the de-duplicated union of General, pinned Workspaces,
  running managed or generic apps, the session-retained selected Workspace,
  and Codex, minus ignored/hidden apps.
- General is always first. Pinned applications follow their saved order.
  Remaining running applications use a stable first-seen order. Codex is last
  unless future configuration explicitly changes that policy.
- `foregroundWorkspaceId` describes Desktop observation.
  `selectedWorkspaceId` describes the Workspace rendered by a specific phone.
  They are not conflated, which allows automatic switching to be disabled and
  supports multiple connected devices.
- When automatic switching is enabled, a stable foreground app selects its
  matching visible Workspace. Unknown, ignored, and transient foreground
  processes do not force a selection.
- When automatic switching is disabled, manual selection is retained for the
  session even if the app stops. If its configuration is deleted or hidden,
  selection falls back to General.
- Pinned, ignored, hidden, recent, custom naming, custom icon, layout assignment,
  and ordering are persisted by Desktop. Running, foreground, and generic
  runtime state are not persisted as truth.

### Workspace activation and unknown apps

- Selecting a Workspace sends `select_workspace(workspaceId)` to Desktop. The
  server validates the ID against its current Workspace state before applying
  it to that client session.
- `Automatically Switch Workspace` defaults to enabled.
- `Activate Desktop App` defaults to enabled. When enabled, selecting a running
  application Workspace brings that app to the foreground.
- Selecting a pinned app that is not running launches it only if the existing
  automatic app-launch preference permits launching. Otherwise LumiaKeys
  changes the layout without launching the app.
- Unknown running applications receive a Generic Layout derived from the
  Desktop-owned default layout. The phone never creates or persists the
  profile.
- Desktop records the unknown app in Recent and offers Create Shortcut Profile
  with Blank and Default starting points. Official templates remain a future
  option and are not exposed as an enabled V1.3 action.

### Desktop Applications and Connection pages

- Extend the existing Apps manager into one Applications page; do not create a
  parallel manager. It contains Running Apps, Pinned Apps, Ignored Apps, and
  Recent Apps sections backed by the same registry.
- Application details support Rename, Change Icon, Assign Layout, Pin/Unpin,
  Hide/Show, Ignore/Restore, and Delete Profile. Destructive profile deletion
  requires confirmation and must repair all references transactionally.
- Add a Connection settings page containing WebSocket Port, Pair Device, QR
  Code, Pair Code, Device List, Connected Phone status, Auto Reconnect, and
  device revocation.
- Add `Automatically Switch Workspace` and `Activate Desktop App` to Desktop
  settings, both enabled by default.

### WebSocket remote protocol and pairing

- Introduce a deep `RemoteSession` boundary shared by Android and iOS. UI and
  controller code consume typed state streams and send typed commands; they do
  not parse WebSocket JSON directly.
- Every message uses an envelope with `protocolVersion`, `messageId`, `type`,
  optional state `revision`, and `payload`. Command responses preserve the
  originating `messageId` for correlation and idempotency.
- Required server messages are `apps_state`, `layout_state`, `active_app`, and
  `action_result`. Required client messages are `select_workspace` and
  `execute_action`. Connection/pairing, state-resume, ping/pong, and icon-asset
  messages may be additional protocol messages.
- `apps_state` contains the ordered Workspace descriptors plus foreground and
  per-session selected Workspace IDs. `layout_state` contains or references the
  current Workspace layout. `active_app` is a lightweight foreground update.
- `execute_action` carries a managed action ID and Workspace context, never a
  raw executable, shell expression, script, or arbitrary shortcut payload.
- `action_result` has success/failure status, a stable result/error code, an
  optional user-safe message, and the resulting state revision when relevant.
- State revisions are monotonic. On connection or revision mismatch, the client
  requests/replays a complete authoritative snapshot rather than applying
  guessed deltas.
- QR pairing carries the Desktop instance identity, reachable endpoint, a
  one-time pairing secret, protocol version, and certificate/public-key
  fingerprint. Pair Code uses automatic discovery to locate the same Desktop
  and then proves the one-time secret.
- Successful pairing issues a revocable per-device credential. Mobile secrets
  are stored in Android Keystore or iOS Keychain; Desktop device records and
  secrets are stored outside the synced manifest in platform-secure storage.
- The persistent session uses an authenticated encrypted WebSocket with the
  paired Desktop identity pinned. Pairing codes expire, are single-use, and are
  never reused as session credentials.
- Auto discovery extends the existing local advertisement with protocol-v3,
  WebSocket, pairing, and Desktop identity capabilities. Discovery alone never
  authorizes commands.
- Auto Reconnect uses bounded exponential backoff and resumes from the last
  accepted state revision. A revoked device cannot resume.
- App icons use content-addressed `iconRef` values. Binary icon data is fetched
  once over the authenticated channel and cached by hash instead of being
  repeated inline in every `apps_state` message.

### Android Hybrid Mode and iOS client

- Introduce an `ActionRouter` deep module. Given platform capability, HID state,
  Desktop session state, action metadata, and routing policy, it chooses exactly
  one executor and returns one result.
- Action metadata adds an execution policy: Automatic, Client HID, or Desktop.
  The phone cannot override a Desktop-only action into local HID execution.
- On Android, Automatic keyboard and media actions prefer connected Bluetooth
  HID. If HID is unavailable and Desktop is connected, supported actions may
  fall back to Desktop. Launch App, Activate App, Open URL/File, Codex,
  Macro, and Script route to Desktop.
- Macro and Script remain rejected by the V1.3 executor until their editors and
  safety models are implemented; their Desktop routing classification is
  reserved now to avoid a later schema break.
- On iOS, every executable action routes to Desktop. Bluetooth HID discovery,
  pairing, status, and Android-only charging/display controls are absent or
  hidden rather than shown as unavailable primary workflows.
- Add an iOS Runner to the existing Flutter mobile project so Android and iOS
  share Workspace rendering, layouts, protocol models, pairing screens, and
  action-result UX.
- iOS starts in No Desktop Connected when no paired reachable Desktop exists.
  It supports QR pairing, Pair Code, automatic discovery, secure credential
  storage, local-network permission messaging, auto reconnect, and device
  revocation handling.

### Codex Workspace and unified Desktop execution

- Codex is represented by the same Workspace/Profile/Layout relationships as
  application Workspaces. Its buttons are fully editable in Desktop.
- Seed the Codex Workspace with Focus Input, Voice Input, previous/next Project,
  previous/next Conversation, Send, Accept, Reject, Continue, Stop, Run Tests,
  Review Diff, Commit, and Terminal. A schema-v1 layout missing the new common
  action IDs is upgraded once; later Desktop edits remain authoritative.
- Replace scattered Desktop action branching with a deep `ActionExecutor`
  interface returning typed `ActionResult` values.
- V1.3 executor adapters cover Keyboard Shortcut, Launch App, Activate App,
  Open URL, Open File, and Media. Open File targets are Desktop-managed IDs
  resolved to user-configured local files; the phone never supplies a path.
- Macro and Script remain reserved/unsupported. No phone message can supply
  raw script text or shell arguments.
- Platform adapters own Command/Ctrl resolution, activation semantics, URL
  opening, media dispatch, permissions, and safe process launch. The registry
  and WebSocket server only pass validated domain actions.

### Persistence and migration

- Manifest schema v2 adds Workspace descriptors/configuration, execution
  policy, dynamic-Workspace settings, canonical app identity, pin/ignore/recent
  metadata, icon references, and editable Codex configuration.
- Runtime `apps_state`, connected sessions, foreground state, and action results
  remain outside the persisted manifest.
- Migration from schema v1 is deterministic and idempotent: existing layouts,
  applications, profiles, icons, and action IDs are preserved; General and
  Codex Workspace records are linked to the existing content; new settings take
  their documented defaults.
- Pairing credentials and Desktop private keys are stored separately from
  exportable layout/profile data.

### On-device shortcut usage

- Android records button, wheel, Desktop-button, and app-launch counts in an
  independent phone preference. No usage field exists in the shared manifest,
  Companion request, `AppConfig`, or Profile transfer schema.
- Settings states that usage never leaves the phone, shows most and least used
  recorded actions, supports clearing the counters, and offers an explicit
  reorder of the current local Profile by descending count.
- Reordering is never automatic. It preserves each button's complete visual,
  feedback, and action configuration and places empty controls after actions.

## Testing Decisions

- Tests assert observable state, protocol messages, persistence, routing, and
  platform-adapter calls. They do not assert private class structure, timer
  implementation, or native API call order beyond documented behavior.
- `RunningAppMonitor` contract tests use fake native event sources to cover
  launch, terminate, foreground change, helper-process deduplication, ignored
  processes, reconciliation, and event coalescing. Separate macOS and Windows
  integration tests validate the native adapters on their host OS.
- `WorkspaceRegistry` receives table-driven tests for ordering, deduplication,
  foreground mapping, pin/unpin, ignore/restore, recent apps, unknown Generic
  Layouts, manual-selection retention, removal fallback, and multiple client
  selections.
- Protocol package tests cover every v3 message round trip, unknown message
  rejection, schema-v1 to schema-v2 migration, invalid references, monotonic
  revisions, managed-ID validation, icon references, and backward-compatible
  v2 decoding where required.
- WebSocket server/client integration tests cover pairing, invalid/expired code,
  certificate identity mismatch, credential revocation, initial snapshot,
  reconnect/resume, missed-revision full sync, action correlation, duplicate
  message IDs, malformed payloads, unauthorized actions, and multi-device
  sessions.
- `ActionRouter` tests cover Android HID preference, Desktop fallback, iOS
  Desktop-only routing, forced Desktop actions, unavailable executors, and the
  invariant that one tap invokes at most one executor.
- `ActionExecutor` tests reuse the injectable process-runner pattern already
  used by Desktop. They cover platform shortcut mapping, launch, activate, URL,
  managed-file opening, media, permission failures, unsupported Macro/Script,
  unknown IDs, and the prohibition on raw paths or shell payloads.
- Desktop controller tests cover Application-page mutations, registry updates,
  settings defaults, transactional reference repair, Generic-to-managed
  promotion, and Workspace broadcasts after state changes.
- Flutter widget tests cover the dynamic top strip, no Settings Workspace,
  General-first/Codex placement, icon rendering, overflow scrolling, runtime
  insertion/removal, selected state, auto switch on/off, manual return to
  General, unknown app UI, action-result feedback, and unchanged landscape
  geometry.
- iOS widget/integration tests cover No Desktop Connected, discovery, QR and
  Pair Code flows, reconnect, hidden HID controls, Workspace rendering, and
  Desktop-only execution. Android regression tests retain existing HID,
  rotation, touchpad, wheel, Profile, and offline behavior coverage.
- End-to-end host tests run on both macOS and Windows with at least two real
  applications. They verify launch/exit detection, foreground auto switch,
  phone selection activating the app, pin persistence, unknown-app Generic
  Layout, and reconnect after Desktop restart.
- Performance acceptance on a normal local network is: stable foreground
  changes reach a connected phone within 500 ms at p95; ordinary action results
  return within 1 second at p95 excluding application launch time; the idle
  monitor is event-driven and does not create sustained high CPU usage.
- Hardware acceptance includes an Android HID-capable phone and an iPhone on
  the same LAN as Desktop. Simulator-only evidence is insufficient for QR
  camera, local-network permission, secure storage, reconnect, or real HID
  claims.

## Acceptance Criteria

1. Launching and closing supported macOS or Windows applications updates the
   phone Workspace strip without manual refresh.
2. The visible strip follows `General | pinned/running apps | Codex`, is
   horizontally scrollable when needed, and contains no standalone Settings
   Workspace.
3. A foreground change selects the matching Workspace on all auto-switch
   clients; disabling automatic switching preserves each client's manual
   selection.
4. Tapping a running application Workspace activates the desktop app when
   activation is enabled and performs layout-only selection when disabled.
5. A pinned Workspace survives application termination and Desktop restart.
6. An unknown application receives a Generic Layout and appears in Desktop
   Recent; Blank or Default promotion creates a persistent editable profile.
7. Applications management can rename, change icon, assign layout, pin, hide,
   ignore, restore, and safely delete a profile.
8. iOS can discover and pair with Desktop using QR or Pair Code, reconnect with
   a stored credential, render dynamic Workspaces, and execute actions only
   through Desktop.
9. Android uses HID for eligible simple actions, Desktop for Desktop-only
   actions, and never executes one tap through both paths.
10. Codex is an editable Workspace using the common Workspace model and ships
    the V1.3 seed action set without overwriting migrated user edits.
11. WebSocket clients receive authoritative state after connection/reconnection
    and receive a correlated `action_result` for every accepted action command.
12. Unauthorized, revoked, unknown-ID, raw-command, and unsupported
    Macro/Script requests fail safely without execution.
13. V1.2 Android offline HID and protocol-v2 Desktop compatibility continue to
    pass their regression suites.

## Out of Scope

- Macro Editor and Macro execution.
- Script Editor and Script execution.
- Official application shortcut templates and template marketplace.
- AI-generated shortcut layouts.
- Cloud sync, accounts, or remote control over the public internet.
- Multi-page layouts, folders, or shortcut folders.
- iOS Bluetooth HID.
- Linux Dynamic App Workspace monitoring.
- Cross-Desktop synchronization of running state or selected Workspace.
- Arbitrary commands, phone-supplied executable paths, or phone-supplied shell
  content.
- App Store, Play Store, or installer release automation unless scheduled as a
  separate release task.

## Further Notes

- Delivery should be sliced by deep module rather than by screen: protocol and
  migration; runtime monitor and registry; Desktop Applications/Connection;
  paired WebSocket sessions; mobile Workspace state; Android Hybrid Mode; iOS
  client; host/device acceptance.
- The Desktop remains the sole authority for synced Workspace, Layout, Icon,
  Profile, Action, application-monitor, and execution state. Phones may cache
  paired credentials and content-addressed icons, but must not become an
  independent configuration source.
- Platform-native monitoring and execution adapters should remain narrow. The
  shared Dart domain layer owns identity normalization contracts, Workspace
  policy, protocol validation, routing decisions, and deterministic tests.
- Existing V1.2 terminology should migrate toward Workspace without renaming
  persisted IDs unnecessarily. A Profile configures a Workspace; a Layout
  defines its buttons; a Workspace is the runtime surface shown on a phone.
