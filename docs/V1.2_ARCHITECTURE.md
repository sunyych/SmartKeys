# LumiaKeys V1.2 Architecture

## Ownership

`DesktopManifest` is the source of truth for Desktop-executed layouts, managed
applications, installed/running state, icon identifiers, and mappings. Desktop
persists it; Android keeps only an in-memory projection. Android `AppConfig`
remains authoritative for the local Bluetooth HID Profiles.

```text
DesktopConfigStore -> DesktopController -> CompanionServer
                            |                    |
                            | execute IDs        | manifest/revision
                            v                    v
                       DesktopActions       CompanionService
                                                 |
                                                 v
                                          Android AppController
                                                 |
                                                 v
                                   Keyboard / Apps / Codex UI
```

The Android `AppConfig` is always used for the existing local key grid, wheel,
touchpad, and Bluetooth HID behavior. A Desktop manifest augments the same top
strip with installed Apps, running-app Workspaces, and Codex; it never replaces
the local Profiles or control geometry.

`ShortcutUsageRepository` is a separate Android-only persistence boundary. Its
private preference is not part of `AppConfig`, Profile JSON, `DesktopManifest`,
or any Companion request, so usage counters cannot leave the phone through an
existing sync/export path.

## Protocol v2

Desktop broadcasts:

- service name and protocol version;
- host name and operating system;
- ephemeral action port and token;
- current manifest revision;
- manifest/apps/codex/icons capabilities.

Android fetches `GET /manifest` with the advertised token. When a later
broadcast or action response reports a different revision, Android fetches it
again. The phone never writes the manifest back.

Android posts one of:

- `button(buttonId)`;
- `launchApplication(applicationId)`;
- `switchProfile(profileId)`.

Application records include `detected`, `running`, and the additive
Desktop-observed `foreground` state. Sync filters out every application not
detected on the current computer. Apps sends only `launchApplication` and then
selects the already-synced layout by application ID; it never receives or sends
an executable path. macOS treats `ChatGPT.app` as the Codex application's
platform alias.

Desktop validates every identifier against its current manifest before
execution. Keyboard shortcuts use `PRIMARY`, resolved to Command on macOS and
Ctrl on Windows. HTTP/HTTPS are the only URL schemes accepted. Macro, Script,
unknown IDs, unknown shortcut keys, and arbitrary shell actions are rejected.

## Transport decision

The existing Bluetooth connection implements the standard Android Bluetooth
HID Device profile for keyboard, consumer-control, and mouse reports. It does
not give the Flutter Desktop process a general Desktop-to-phone payload stream.
V1.2 therefore keeps HID for input and uses the existing local companion
channel for structured, bidirectional control data.

A Bluetooth-only successor requires a separately engineered transport, such as
a BLE GATT service or vendor-defined HID reports plus native Windows/macOS raw
HID clients. `CompanionService` and the shared protocol isolate that future
change from UI and manifest ownership.

## Future-compatible schema seams

- Target enums already reserve Macro and Script.
- Layout kind separates Keyboard, Application, and Codex.
- Apps reference layouts by ID rather than embedding UI state.
- Profiles reference layouts and optional app/platform selectors.
- A schema version and monotonic revision support later migrations.

Multi-page layouts, folders, cloud sync, import/export, automatic foreground
app switching, AI layout generation, and official app templates remain outside
V1.2.
